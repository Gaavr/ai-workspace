# Задачи по проектам

Задачи лежат Markdown-файлами в git-репозитории задач (путь по умолчанию `~/Projects/ai/tasks`, меняется переменной `TASKS_REPO`). Читает и двигает их команда `tasks`. Проект и путь к его репозиторию описаны в `projects.yaml` в корне репозитория задач.

## Когда применять

- Просят посмотреть, разобрать или взять задачи: «посмотри задачи», «что по Grams», «начни задачу 42», «возьми следующую».
- Просят отметить результат: «задача 42 готова», «закрой 42», «отмени 42».

Не нужен, когда пользователь сам описал, что делать, и не упоминает задачи.

## Порядок

1. `tasks list --json`. Нужен один проект — `tasks list <проект> --json`. Покажи пользователю кратко: номер, проект, тип, статус, заголовок.
2. Выбери задачу. Назвал номер — бери его. Сказал «возьми следующую» — предложи самую старую со статусом `todo` или `inbox` и дождись подтверждения. Задачи со статусом `in_progress` и `queued` чужие, их не бери.
3. `tasks show 42`. В конце вывода — пути скриншотов и путь к репозиторию проекта. Задача слишком короткая или противоречит коду — спроси пользователя, не угадывай.
4. Скриншоты: модель видит картинки — открой каждый файл инструментом чтения изображений. Не видит — опирайся на строки «Описание скрина» в тексте задачи. Описания нет — скажи об этом пользователю.
5. `tasks start 42`.
6. Работай в репозитории проекта (путь из `tasks show`) в отдельной ветке `task/<номер>-<slug>`, например `task/42-sortirovka`. Slug — из имени файла задачи. Если в репозитории уже используются worktree, создай ветку в новом worktree, а не в основной папке.
7. Проверь работу: тесты проекта. Для iOS-проектов (в `tasks show` помечены `iOS`) собери проект `xcodebuild` нужной схемы. Не прошло — чини, а не отмечай готовой.
8. Сделай коммит в ветке задачи. Сообщение коммита — по правилам проекта, в нём номер задачи.
9. Результат:
   - Нужно ревью: запушь ветку, открой pull request (`gh pr create`), затем `tasks review 42 --pr <URL> --branch task/42-sortirovka`.
   - Ревью не нужно (вопрос, правка без кода): ответь пользователю и `tasks done 42`.
   - Работа невозможна или пользователь отказался: `tasks cancel 42` только по его слову, иначе оставь задачу как есть и расскажи, что мешает.
10. Скажи пользователю итог: что сделано, ссылка на PR, что проверено.

## Чего не делать

- Не мержить pull request и не пушить в основную ветку проекта. Мерж делает пользователь.
- Не брать две задачи сразу: сначала закончи или верни текущую.
- Не править файлы задач руками, меняй только через `tasks`: он коммитит и пушит сам.
- Не трогать чужие задачи и задачи других проектов, о которых не просили.
- Не отмечать `done` и `review`, пока не прошла сборка и тесты.

## Если `tasks` не установлен

Репозиторий задач — обычные Markdown-файлы: `<проект>/NNNN-<slug>.md`, статус и заголовок в шапке (`status:`, `title:`), скриншоты рядом в `<проект>/attachments/`. Сделай `git pull`, прочитай файлы напрямую. Статус меняй в шапке файла, добавь строку в раздел «Журнал», сделай коммит и запушь. Установка CLI описана в README проекта task-inbox: `uv tool install --editable ~/Projects/ai/task-inbox`.

## Проверка результата

`tasks show 42` показывает нужный статус (`review` с ссылкой на PR или `done`), ветка `task/42-…` запушена, основная ветка проекта не тронута.
